# Buyer-cycle reliability release 2026-11-23

## P0/P1 fixes

- Commerce readiness now requires an open launch switch and at least one receiving destination. Order creation checks this before consuming its rate-limit allowance, then locks and snapshots the destinations in the reservation transaction.
- New orders retain their InstaPay/mobile-wallet instructions. Payment submissions are checked against that order snapshot; legacy orders with both snapshot fields `NULL` use only currently configured destinations.
- Marketplace browsing remains available while reservation is visibly disabled. Settings raises an invariant warning if an existing database has `launch_open=1` without a destination.
- Demo login requires both `app_env=demo` and explicit demo mode. A configured demo environment can open without Twilio; production still requires Twilio and refuses training data.
- Successful member/demo/staff/setup authentication rotates the session and clears the opposite principal.
- Supplier-party reuse rejects ownership conflicts, public publication is limited to the approved four-material catalogue, and zero/recovered stock transitions to `depleted`/`inspected`.
- Apache deny files and the private proof-storage placeholder are restored and repository-tested.
- Authenticated buyer demo personas can complete reservations without a real receiving account. Their server-side session marker uses immutable `DEMO-ONLY-NO-TRANSFER` instructions and explicit no-money warnings. Demo payment, approval, cancellation and settlement references are generated server-side; admins use dedicated synthetic-approval controls and never claim that money moved. Normal members, supplier personas, staff sessions, and all production environments still require real commerce readiness.
- Real incoming and outgoing transfer references now require 6–100 safe characters and duplicates are rejected with a domain message before persistence. Two-character values such as `12` are not accepted as financial references.

## Upgrade

1. Back up the database and `htdocs/storage/proofs/`.
2. Apply `htdocs/database/migrations/20261123_002_order_payment_snapshot.sql` exactly once and verify `schema_migrations.version`.
3. Deploy the source, including every `.htaccess` and `htdocs/storage/proofs/.gitkeep`; do not deploy `tests/`, `tools/`, or credentials.
4. In Settings, verify at least one payment destination before leaving launch open. Place a test reservation and confirm its order page retains the expected destination.
5. Clear PHP opcode cache if the host provides one.

Fresh installations import only `htdocs/database/schema.sql`. Rollback requires restoring the backup because source rollback cannot remove or reinterpret captured payment instructions safely.
